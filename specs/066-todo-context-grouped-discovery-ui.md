# 066 — Context-grouped discovery UI (059-followup)

**Status:** todo · Linear [BOL-895](https://linear.app/iskeru/issue/BOL-895) · build branch `moacyrricardo/bol-895-cpt-066-context-grouped-discovery-ui` · **Part of concern 064 (mockup delivery).** **Builds on 063 (done)** — the DTO seam this spec renders — and lands **after sibling 067** (Screen C), which owns the recipe-list composition and the filter bar this spec re-homes over context cards.

## Context

This spec is **exactly what 059 deferred**, now buildable. 059 (`moacyrricardo/bol-888-cpt-059-app-model-ui-new-surfaces`, merged — spec **059 is `done`**) set out to render discovery grouped by 055's app contexts, and its Implementation Notes recorded the wall it hit: the context model — `contextDisplay`, `scriptFolder`, `contextScripts`, `sourceNote`, `confidence` — is persisted on the recipe's `app_port_list` CLOB but was stripped at every client-facing DTO. **063** ([063](063-done-native-consumer-and-context-dto.md), `done`) closed that seam: it widened the read aggregate `MonitorService.AppPort` to the full context payload — today a **ten-component** record `AppPort(appName, port, runtime, contextKey, contextDisplay, contextScripts, sourceNote, confidence, scriptFolder, managementPort)` (`monitor/service/MonitorService.java:100–121`), *not* the pre-063 `(appName, port, runtime)` triple — added the shared wire record `RecipeDtos.AppPortView` (`recipe/api/RecipeDtos.java:104–125`, now carrying the same context fields plus 073's `managementPort`), added `RecipeView.appPortList : List<AppPortView>` (`RecipeDtos.java:65–77`), and derived **native consumers** (`NativeConsumerData`, grouped by `contextKey`, `source=NATIVE`) feeding `MonitorDtos.MonitorConsumerView` via `ofNativeConsumer` (`MonitorDtos.java:279–315`), replacing the old one-consumer-per-`appName` `ofNativeApp` mapping (`MonitorDtos.java:292`). 063 was **seam-only by decision** (its D5): it carries the data end-to-end on `/api/monitor` but **explicitly handed the recipe-read population and every surface to this spec** (063 Implementation Notes, `specs/063-*.md:141–145` — "Parsing the recipe's `app_port_list` at the recipe-read endpoints to render per-context records is the 059-followup's rendering job (D5)"). **066 is that rendering job — and it inherits the wiring 063 left undone (see the two blockers below).**

The surface being extended is the machine-detail Discovery panel, `discoverySection(p, mid, families)` (`app.js:753`): today a `.section` with per-family `.filter-chips` toggles (`toggleFamily` PUT `/machines/<mid>/discovery/<key>`, `app.js:805`) and a "Discover recipes" button — no grouped list at all. Proposed actions render flat in the recipe groups that `screenMachineDetail` assembles from the recipe channel (`data.groups`, built from `GET /recipes?machineId=` at `app.js:611–621,642`). The target experience is the mockup's **Screen B** (`054-assets/mockup-compute-admin.html:581–765`): one `.ctx` card per context with a mono path header (`.ctx-path`, :619), a source note (`.ctx-src`, :620 — "app folder · discovered via port :8080 + systemd unit"), and per-action rows with an "Approve → add recipe" button (:635). The mockup's `.dbadge` footprint metrics on those cards (:622–627) and its `.act-verb` chips (:631) are **design forks recorded in concern [064](064-concern-mockup-delivery.md)** — see Known Gaps.

**Sibling ordering — 067 first, then 066.** [067](067-todo-machine-dashboard-composition.md) (Screen C) composes the machine-detail page — the recipes-&-actions grid plus a **search box + type/source filter chips over `data.groups`** (067 dec 4, `app.js:642`; source chip keys on 063's `AppPortView.runtime`). 067 explicitly leaves the context-grouped discovery regroup to 066 (067 Context). Build order is therefore **067 → 066**: 067 lands the flat recipe grid and its filter bar; **066 then relocates the discovery-pre-filled action rows out of that flat grid into context cards, and re-homes 067's type/source filter bar over the relocated cards** (see Decision 5 / Known Gaps).

## Decision

1. **Discovery renders as Screen B: one context card per resolved context.** Grouped by 055's `contextDisplay` (via 063's widened `RecipeView.appPortList`, once populated per the Implementation below), each card carries: the **logical path header** (mono, the `crumbs`/mono idiom, `app.js:276`), the **source note** (063's `sourceNote`) as a dim sub-line, the **sibling-script list** (055 dec. 4, 063's `contextScripts`) by basename, and the record's **confidence** rendered as a text label/badge — never colour alone (the WCAG house rule, `app.css:751`). This restates 059 Decision 1 and builds it for real.
   - **Non-listening / declared-only items.** `AppPortView.port` is a **primitive `int`**, so a context can never have "an empty port list" — spec-056 emits a non-listening app with the sentinel `port = 0` (`discovery/AppPortItem.java:37–42`). Treat any `port == 0` item as **declared-only**: render it with a "no listening port" text label, exclude it from any port line/badge and from anything poll-shaped (it has no socket to probe). A context whose members are all `port == 0` is a declared-only card.

2. **Per-action approve-to-add reuses the EXISTING spec-044 approval path — no new endpoint.** Each proposed action row inside a card gets the mockup's "Approve → add recipe" affordance, implemented as the existing `approvalSplit(machine, recipe, action)` control (`app.js:703`) — `DRAFT`→Submit, `PENDING_APPROVAL`→Review & approve via `openActionDrawer`/`screenApproval` (`app.js:937`/`app.js:974`), all through the existing `POST /actions/<id>/<verb>` (`actVerb`, `app.js:740`). The gate stays singular and UI-only (ARCH gate point 2); 059's note that spec-044 already satisfies this holds — 066 relocates the rows into context cards, it does not add an approval mechanism.

3. **Context identity comes from `RecipeView.appPortList`, which 066 must first populate at the recipe-read endpoint.** The proposed actions (rid/aid/approvalState) already arrive on `data.groups` (`app.js:611–621,642`, from `GET /recipes?machineId=`). 066 **re-groups `data.groups` by the context fields on each recipe's `appPortList`** to attach each action to its card — no new endpoint, no payload added to the discovery channel. **But on merged `main` that list is empty** (see BLOCKER, Implementation): `GET /recipes` maps through the single-arg `RecipeView.of(recipe)`, which passes `List.of()`. So 066 has a **server-side component**: parse the recipe's stored `app_port_list` into `List<AppPortView>` and call the two-arg `RecipeView.of(recipe, parsed)` in `RecipeRS.list`. This is presentation *plus* a small recipe-module parser + wiring — **not** "app.js/app.css only".

4. **Surface-2: the Monitor dashboard aggregates native consumers per context — a real aggregation layer, not a legend rename.** 063 emits one `NativeConsumerData` per context (grouped by `contextKey`, `name = contextDisplay`, carrying `appNames`), surfaced as a `MonitorConsumerView` whose `id = name = contextDisplay`. **The client poll pipeline is `(appName, port)`-keyed, one app per consumer**, so a per-context consumer does not currently poll at all (see BLOCKER). 066 turns the per-context consumer into an **aggregation over its member apps**: fan the poll out per member app (each member's own `(appName, port)`), then **sum PSS/CPU/du across the members into the context's three axes**. The tri-axis meters, legend, and OTHER remainder (`axisMeter` `app.js:2476`, `consumerLegend` `app.js:2511`, `computeOther` `app.js:2454`) stay structurally the same — `computeOther`'s `attr()` blindly sums rendered consumers (`app.js:2455–2458`), so a per-context aggregate segment subtracts from OTHER by the same construction (057's single-denominator invariant, not re-implemented). What is **not** untouched: `buildConsumers`' app-join and the poll fan-out (both rewritten — see BLOCKER 2 in Implementation).

5. **The per-family `.filter-chips` stay, and 067's type/source filter bar is re-homed over the context cards.** The family enablement bar (`app.js:754–762,800`; `.tag--filter`, `app.css:244`) remains as a filter above the grouped cards — grouping and filtering coexist (059 Decision 1's coexistence rule); a context card shows when its discovering family is enabled. Separately, because 066 **relocates the discovery-pre-filled action rows out of 067's flat recipe grid into context cards**, 066 must define how 067's **type/source filter chips** (067 dec 4 — recipe `type` values and native/docker `source` on `AppPortView.runtime`) apply to the relocated cards: a context card shows when it holds at least one action whose recipe type is selected and whose member `runtime` matches the source filter. 066 owns this re-homing (see Known Gaps / [067](067-todo-machine-dashboard-composition.md)).

6. **No footprint badges on discovery cards.** The mockup puts DISK/RAM/CPU `.dbadge`s on `.ctx-head` (mockup `:622–627`); 059 Decision 1 moved footprint to the Monitor route (poll data, not sweep data). That conflict is a concern-064 **Open Question** — 066 defers to it and builds cards with identity + structure only, linking to Monitor for live footprint.

## Implementation

Client work is in `src/main/resources/static/{app.js,app.css}`; there is **also a server component** (Decisions 3 and 4 — the `appPortList` population and the `ofNativeConsumer` widening). Build the client through `h()` (`app.js:23`), never `innerHTML` (spec-012 XSS discipline: host-derived strings — paths, source notes, script names — reach the DOM only as text). **Restart `spring-boot:run` for every front-end edit** (target/classes skew; project CLAUDE.md "UI evidence").

### BLOCKER 1 — populate `RecipeView.appPortList` at the recipe-read endpoint (server)

Without this, D3 renders **zero** context cards on a faithful build (and the JS harness still passes, because it feeds mock data): `GET /recipes?machineId=` → `RecipeRS.list` maps each recipe through the single-arg `RecipeDtos.RecipeView::of` (`recipe/api/RecipeRS.java:54`), which delegates to `of(recipe, List.of())` (`RecipeDtos.java:68–70`) — `appPortList` is always empty. There is **no main-code caller of the two-arg `of(Recipe, List<AppPortView>)`** overload (verified); 063 added it as a population hook and left it unused.

- **Add a parser in the recipe module** that turns a recipe's stored `app_port_list` CLOB (`Recipe.getAppPortList()`, `recipe/model/Recipe.java:95`) into `List<AppPortView>`, reading the same rich context fields (`contextDisplay`/`contextScripts`/`sourceNote`/`confidence`/`scriptFolder`/`managementPort`) and tolerating null/blank/malformed → empty list.
- **Call the two-arg overload in `RecipeRS.list`:** `RecipeView.of(recipe, parsed)` per recipe.
- **Constraint that forces a recipe-module parser (do not "just reuse" the monitor one).** The equivalent parser already exists as `MonitorService.parseAppPortList` / `addAppPorts` — but both are **private**, and the module dependency direction is **monitor → recipe** (the very cycle that made 063 relocate `AppPortView` down into `recipe`). `RecipeRS` (the lower module) therefore cannot call into `monitor`. The parser must **live in / be duplicated into the `recipe` module** — the same deliberate-duplication posture 063 took for the datastore token list. `AppPortView` already lives in `recipe/api/RecipeDtos`, so nothing new crosses a boundary.
- **Add a server test** for `RecipeRS.list` / the new parser: a recipe with a persisted context-ful `app_port_list` yields a `RecipeView` whose `appPortList` carries the parsed items (context fields + `managementPort` populated); a bare/old/blank list yields empty. (063 owns the `/api/monitor` DTO tests; this is the recipe-read path 063 did not wire.)
- **Alternative considered, not chosen.** 066 could instead fetch `GET /api/monitor`, whose `MonitorActionView.appPortList` **is** already populated (`MonitorDtos.java:404–409`, via `appPortView`) and regroup from there. Rejected: that is a different data plan than D3 (discovery cards are assembled from the recipe channel `data.groups`, not the monitor channel) and would couple the machine-detail Discovery panel to the monitor read. The population fix above keeps D3's single data plan.

### BLOCKER 2 — per-context native consumers must actually poll (server + client)

Decision 4 says "aggregate over member apps"; today a per-context native consumer **polls nothing and renders all axes as `—`** — a live gap already present on merged `main`, which 066 inherits and must fix:

- The poll join is per-app: `buildConsumers` builds `appsByName[a.appName]` and joins `appsByName[c.id] || appsByName[c.name]` (`app.js:2412–2416`). A 063 per-context consumer has `id = name = contextDisplay` (`MonitorDtos.java:312–315` — `ofNativeConsumer` sets both to `n.name()`, and `n.name()` is the `contextDisplay`), which matches **no** `appName` → `app = null` → `port = null`, `checks = []`.
- `pollConsumers` then filters `(c.checks || []).length && c.port != null` (`app.js:2750`), so the per-context consumer is **dropped from the poll** → its axes stay `—`.
- **Fix (membership source).** Widen the server so the consumer carries its member app identities, then aggregate on the client:
  - **Server:** `NativeConsumerData` already carries `appNames` (`MonitorService.java:133–135`), but `MonitorConsumerView.ofNativeConsumer` **drops it** (`MonitorDtos.java:312–315`). Add an `appNames` field to `MonitorConsumerView` (or an equivalent member list) and copy `n.appNames()` through. This is the robust membership source — **preferred over** a fragile client-side split of the `contextDisplay` string.
  - **Client:** rewrite `buildConsumers`/the poll fan-out so a consumer with member `appNames` fans the probe out **per member app** (each member's own `(appName, port)` — the member ports come from the recipe's `appPortList`, which the consumer's context maps to), then **sums PSS/CPU/du across members** into the context's `ram`/`cpu`/`disk`. A single-app context degenerates to today's one-app behaviour.
- **Strike "structurally untouched"** for Surface-2: `buildConsumers` and the poll path change; only `axisMeter`/`consumerLegend`/`computeOther` are reused unchanged.

### Context cards inside `discoverySection`

- Keep the existing family bar + Discover button (`app.js:753–801`) untouched at the top of the `.section`.
- Below them, build the grouped list: index `data.groups` (`app.js:642`, now with a populated `appPortList` per BLOCKER 1) by each recipe's `appPortList[].contextDisplay`; one `.card`-scaffolded context card per distinct context, **ordered stably** (e.g. by display path — see the 073 stale-duplicate Known Gap for why the order must tolerate a duplicate probe row-set).
- **Card header:** the `contextDisplay` path in the mono idiom; `sourceNote` as a `.small dim` sub-line; a text confidence label (`high`/`low`/…) rendered as a neutral `.tag` — chip semantics reserved for approval states (`chip()`, `app.js:197`; state map `app.js:188`).
- **Card body:** the `contextScripts` basenames as a compact list; then one row per proposed action — action label + argv summary (text), a **port line** for the item (see 073 below), its approval-state chip, and the `approvalSplit` control (`app.js:703`) verbatim. After approval, the existing reconciliation shows the recipe in the normal list; nothing bypasses `screenApproval`'s review path (`approvalSplit` forces "Review & approve" when unreviewed, `app.js:717–722`).
- **073 — management port on the per-item port line.** `AppPortView` is post-073 a nine-field record ending in `Integer managementPort` (`RecipeDtos.java:104–107`; semantics in `discovery/AppPortItem.java:49–55`). Render the item's port line as `:T` — or, for an actuator-merged Spring Boot app whose management port differs, `:T · mgmt :M` — **mirroring the Monitor badge** (`app.js:2607–2613`). The shape changed with 073: a split-management-port app was pre-073 discovered as **two** `AppPortItem` records (traffic + management); post-073 it is **one** `springboot` record whose identity is the traffic port, with `managementPort` recorded and its four actuator probe rows binding the `management-port` param. Any rendering example/test uses this merged single-record shape.
- **Fallbacks (063's tolerant-reader contract):** a group whose `appPortList` is empty or context-less (old rows, or a recipe with no pre-fill) renders in an "ungrouped" trailing section styled like today's flat groups — no data is hidden by the regroup.
- **Declared-only items** (`port == 0`, D1) get a "no listening port" text label and no port line.

### Surface-2 grouping (client, after the BLOCKER-2 server change)

- The consumer model assembly maps `MonitorConsumerView`s generically; 063's per-context native consumers flow through, now carrying `appNames`. 066's delta: surface `contextDisplay` as the consumer's display name in the legend chip and drawer title, list the context's `contextScripts`/member apps in the drawer body (`openConsumerDrawer`, `app.js:2961`), and drive the tri-axis meters from the **per-member aggregated** poll (BLOCKER 2). The per-`appName` native cards are replaced; the "native process — no attributable disk footprint" caveat (`app.js:2980`) now applies per context.
- `computeOther` (`app.js:2454`) is reused unchanged; the 059 low-confidence text badges — `isLowConfidence`/the "low confidence" tag (`app.js:2537–2538,2560`), fed by `_ramLow`/`_diskLow` (assigned `app.js:2848,2856`) — are reused unchanged.

### Styling

New CSS is limited to context-card layout (path header / source-note sub-line / script list / action rows), through existing tokens and classes (`.card`, `.section`, `.tag`, `.chip--*`, `.filter-chips`, spec-043 breakpoints `app.css:133,806`). The mockup's `.dbadge`, `.ctx-*` skin, and `body[data-identity="iskeru"]` rounding (mockup `:389–397`) are **not** ported — visual identity is spec 065.

### Tests

- **Server:** the BLOCKER-1 recipe-read population test (above), and — if `MonitorConsumerView` gains `appNames` — a mapping assertion that `ofNativeConsumer` carries the member app names through.
- **Client:** extend `src/test/js/app-model-ui.render-check.js` (the 059 harness): grouping of `data.groups` by `appPortList` context fields (multi-recipe context, context-less fallback, `port == 0` declared-only label, the `:T · mgmt :M` port line); the approve control on a grouped row is `approvalSplit` output; a per-context native consumer renders one legend chip named `contextDisplay` **and** polls its member apps (axes are numbers, not `—`, given member readings).

## Known Gaps

- **073 stale-duplicate ordering.** Until spec-036 rewrites stale discoveries, a machine can still carry a lingering **pre-073 `http app monitor` recipe** alongside the new merged `springboot` one for the same app; both fall into the **same context card** as a duplicate probe row-set. The card's row/context ordering must be **stable and tolerate the duplicate** (deterministic sort key, e.g. by context display then action name) rather than assuming one probe set per context. Called out so the build does not render a jittering or de-duped-incorrectly card.
- **Footprint badges on discovery cards are a concern-064 Open Question.** The mockup shows them; 059 Decision 1 says no (poll data belongs to Monitor). Deferred — this spec ships without them; if 064 resolves the other way, the badge row is a small additive follow-up.
- **067 owns the recipe grid and its filter bar; 066 re-homes that bar over the context cards.** Build **after 067**. 066 relocates the discovery-pre-filled action rows out of 067's flat `data.groups` grid into context cards and must apply 067's type/source filter chips to the relocated cards (Decision 5). See [067](067-todo-machine-dashboard-composition.md).
- **Verb badges on action rows (mockup `.act-verb`, `:631`) are not built** — there is no verb field in the model; the closed verb vocabulary is 053/060 scope (a 064 fork). Rows show the action label the discoverer proposed.
- **Declared apps (mockup's DECLARED card, `:748`) are 053 scope, unbuilt** — no declared-context card renders until that model exists (a 064 fork). (Distinct from the `port == 0` declared-only *item* in D1, which 066 does render.)
- **`contextKey` is never fetched or rendered** (063 D3): the UI keys on `contextDisplay`; the internal S9-secret dedup key stays server-side (no DTO carries it — `MonitorConsumerView` gains `appNames`, never `contextKey`).
- **Visual identity is 065**: these cards render in the existing spec-012 slate/teal system; the rounded iskeru skin is not this spec's work.
