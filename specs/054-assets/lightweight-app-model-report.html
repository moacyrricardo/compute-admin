Lightweight App-Metadata Model

A clean-slate feasibility blueprint for SSH-Linux hosts

This report tests one idea end to end: that an app on a Linux box can be described by a small, purely-mechanical triple — an app-script, the folder it lives in, and the app/context folder that owns it — and that from that triple alone we can group scripts and probe disk, RAM, CPU, and (for Docker) database usage. It deliberately ignores what compute-admin has already built or spec'd; it asks only what is true and reachable over SSH on a real Linux host. Four Linux-systems investigations feed it — discovery, mapping, probing, and the Docker/common-service layer — and they interlock as one pipeline.

Verdict — the model holds, and most of it needs no root

The triple is feasible and largely deterministic. Apps are discoverable by listening ports and by Docker; the script→context derivation is a fixed wrapper-directory rule with a handful of documented failure modes; and every resource axis has a concrete probe whose cost and privilege are known. The single most consequential design fact: ~80% of the map is obtainable as an ordinary login user — sudo buys you other users' process internals and Docker/volume internals, and every privileged probe has a labelled, degraded fallback. The two calls you actually have to make (not discover) are the symlink identity key and how aggressively the wrapper rule hops; everything else is mechanism.

◆How the four pieces interlock

Nothing here is standalone. Discovery emits a raw record per candidate app; Mapping turns that record's path signals into a context and its sibling scripts; Probing measures each context. The Docker/service layer is not a fourth stage in series — it feeds all three: it resolves container identity for discovery, hands host paths to mapping, and tells probing which volumes to measure.

◆The data model that flows through it

One record is emitted per app-script at discovery; mapping collapses app-scripts that resolve to the same context; probing hangs metrics off the context. The operator's worked example — two scripts, one under scripts/ and one at the root, both belonging to /opt/lab/app1 — is exactly the grouping the model must produce.

1Discovery — finding the apps

Two independent sweeps, unioned: listening ports and Docker. The port sweep enumerates listeners, then resolves each socket → PID → filesystem identity (exe, cwd, cmdline). The full port inventory is unprivileged; only the port→PID join for other users' sockets needs sudo. Common services (nginx, mysql, mariadb, postgres) are then fingerprinted by process/exe → port → package, with two agreeing signals treated as confident.

The routing rule that everything depends on: read /proc/<pid>/cgroup before trusting exe/cwd. A containerized PID's host-side paths are overlayfs internals (/var/lib/docker/overlay2/…) — never a real app-folder. cgroup tells you container vs systemd-unit vs session in one world-readable read, and routes the record to the Docker branch.

The two blind spots that would otherwise lose apps

  • DNAT / docker-proxy ports — a published container port may be owned by docker-proxy, or by no host process at all (iptables owns it). Any port docker ps reports but ss can't attribute must be resolved through the Docker branch, not /proc.
  • Non-listening apps — queue workers, cron jobs, batch scripts never appear in a port sweep. Mandatory complements: systemctl list-units --state=running, cron enumeration, and a full ps -eo args interpreter-pattern scan. They emit the same record with an empty port list.

2Mapping — script → script-folder → context

Given a discovery record, derive the script-folder (where it lives) and the app-folder / context (who owns it) with no LLM — pure heuristics. The core is the wrapper-directory rule: if the script sits directly under a wrapper dir (scripts, bin, sbin, frontend, backend, cmd, dist, build, …), the context is the parent of that wrapper; otherwise the context is the script-folder itself. One hop by default; a second hop is allowed only when the intermediate dir is also a wrapper and the target carries a marker file (.git, compose.yaml, package.json…).

Evidence — the algorithm, step by step (procfs → canonicalize → hop → clamp)

Step 0 — normalise to a script path. PID-based: readlink /proc/<pid>/exe; if the basename is an interpreter (python*, node, ruby, java, bash, gunicorn…), discard it and parse cmdline for the real script, resolving relative paths against /proc/<pid>/cwd. python -m pkg / -c '…' have no file → fall back to cwd. Docker: translate WorkingDir through the longest-prefix bind Mount to a host path; if no bind covers it, the container is the context (docker://<name>) — never walk the overlayfs upperdir.

P=$(realpath -m "$S"); SF=$(dirname "$P"); AF=$SF
case "$(basename "$SF")" in
  scripts|script|bin|sbin|libexec|tools|frontend|backend|cmd|dist|build|out|target|app|src)
    par=$(dirname "$SF")
    case "$par" in /|/opt|/srv|/home|/usr|/var|/etc|/usr/local) ;; *) AF=$par;; esac;;
esac

Steps 1–4: canonicalize (realpath -m tolerates (deleted)), take dirname for the script-folder, apply the single wrapper hop, then clamp — if the hop would land on / or a bare convention root, revert to the script-folder. Step 5 (advisory): a marker file at the candidate raises confidence and gates the bounded double hop; it never reverts a hop.

Evidence — symlink policy & sibling enumeration

Symlinks. Resolve file-level links fully and key dedup on the physical path, but display the logical (unresolved) path; when the physical path matches */releases/* or */versions/* (a current→releases/<ts> deploy symlink), promote the context key to the logical one so a redeploy doesn't fork a new context every release. This is a design call — see §Design.

Siblings. Enumerate other runnable entry points under the context so they group:

find "$AF" -maxdepth 3 -xdev \
  \( -name .git -o -name node_modules -o -name .venv -o -name target \) -prune -o \
  -type f \( -perm -u+x -o -name '*.sh' \) -print 2>/dev/null | head -200

-maxdepth 3, -xdev (never cross into mounted data), prune dependency/build dirs before matching (node_modules alone is thousands of executables), hard head -200 cap. Hitting the cap is a signal the hop overshot (landed on /home/user) → flag "too broad". Classify each hit by first bytes: #! = script, \x7fELF = binary.

Evidence — the 8 failure modes (what breaks the heuristic)
  • Interpreter-launched — exe is python3; without the interpreter-skip every Python app groups under /usr/bin. -m/-c have no file → cwd fallback; a systemd service with cwd / → recover via systemctl show <unit> -p WorkingDirectory,ExecStart.
  • Deleted/replaced files — exe → …(deleted) after redeploy; strip + realpath -m, mark stale=true. Still the right grouping key.
  • Monorepos — backend/scripts/run.sh double-hops to the repo root, merging frontend+backend. By design per the operator's frontend/backend rule; git-rooted monorepos group at the repo root — document it, don't call it a bug.
  • src/app members — riskiest of the wrapper set; the clamp covers top-level /src, /app. Drop these two first if false grouping shows up.
  • procfs permission-denied — non-root can't readlink other users' exe/cwd; degrade to cmdline-only, emit confidence=low, reason=procfs-denied rather than guess.
  • Overlayfs host paths — a container PID's exe resolves into /var/lib/docker/overlay2/…; detect the prefix and re-route to the Docker branch.
  • Busybox / multi-call / bash -c — no file path exists → cwd fallback; if cwd is /, an explicit unknown/<comm> bucket beats a wrong deterministic answer.
  • Vendor levels (/opt/acme/app1) — handled: acme ∉ wrapper set, single hop lands correctly.

3Probing — disk, RAM, CPU, DB per context

Each axis measures a different kind of thing, and conflating them is the classic mistake. Disk is per-context state (no sampling, just cadence). RAM is per-script instantaneous state, summed to the context. CPU is a rate — meaningless from one sample. DB (Docker only for now) is two independent numbers, logical and physical.

PSS, not RSS. Summing RSS across 8 workers sharing 200 MB of libraries overstates by up to 7×200 MB. /proc/<pid>/smaps_rollup → Pss divides each shared page by its sharers, so PSS values sum correctly. RSS is the world-readable fallback only, labelled "≤ upper bound" — never presented as the same metric. Pick one per script type: native → Σ PSS, docker → cgroup / docker stats, and never sum a container's cgroup number and the PSS of PIDs inside it (same bytes twice).

Evidence — disk, and the double-counting rule

Run du under timeout 120 nice -n19 ionice -c3 so a giant tree degrades the probe, not the host. Because du -s prints only at the end, a plain timeout yields nothing — on timeout, fall back to du --max-depth=1 per child with per-child timeouts, summing what completes (a lower bound plus which subtree blew the budget). Cache and re-measure on a slow cadence.

Docker disk = writable layer + Σ named volumes + Σ bind paths (image size reported but never summed across contexts — shared layers). Volume sizes: docker system df -v, or root du on /var/lib/docker/volumes/<vol>/_data, or the no-root fallback docker run --rm -v <vol>:/v:ro alpine du -sb /v.

Double-counting rule: when a volume/bind lives under an app-folder (common: ./data:/var/lib/postgresql/data), naive du(folder) + per-volume counts those bytes twice. Context disk = du(app-folder, excluding every mount source under it) + Σ(each mount counted once), deduped by resolved realpath. Cross-check mounts the parser missed with findmnt -rn -o TARGET.

Evidence — CPU (the interval trap) & the DB double-measure

CPU. Take both samples inside one SSH exec: sample all PIDs+cgroups → sleep 4 → sample again → emit both with date +%s.%N stamps, and divide by the measured Δt (not the nominal sleep). Two SSH round-trips would add seconds of jitter to Δt. Avoid ps -o %cpu — it's a lifetime average: a worker that burned CPU for its first hour then idled for a week shows high forever. Interval choice: 3–5 s is responsive without aliasing against periodic workloads.

DB (docker only). Report both: logical (pg_database_size() / information_schema sum — MySQL 8 serves cached stats, prepend SET SESSION information_schema_stats_expiry=0 for fresh) and physical (the data volume's du). They legitimately disagree — physical ≥ logical, and the gap is a signal (WAL/binlog/bloat). Credentials come from the container env (docker exec <cid> printenv POSTGRES_USER / MYSQL_ROOT_PASSWORD); if secrets were injected via file/mount, the probe needs a per-app credential hint. Standalone-DB sizing is explicitly out of scope for now — same SQL, different transport later.

4Docker & common-service extraction — no parser to build

The operator's instinct ("maybe we need a Dockerfile parser") resolves cleanly: don't parse source — inspect the live engine. The hosts already run Docker, so docker inspect / docker compose config return resolved facts (real host paths for bind mounts, real published ports, effective env) that a source parse only approximates. The one dependency we adopt is the Docker CLI already on the target, consumed as JSON.

Inspect live, parse source only for the not-running tail. A running container's Mounts[] beats parsing VOLUME + compose volumes — it's the merged, resolved result including ad-hoc -v flags no file mentions. docker image inspect already surfaces everything the Dockerfile baked in. Parse the compose file (via the engine's own docker compose config) only for services defined but not running, or to diff declared-vs-live. Raw-Dockerfile parsing is the narrow tail, served by building/pulling then inspecting the image.

◆The calls you actually have to make

Almost everything above is mechanism — determined by Linux, not by preference. These few are genuine choices the model has to commit to. They are decisions, not facts, so they're carried into a companion decision surface ↗ where you can weigh the evidence, pick, and emit an execution prompt; here they're only surfaced.

Decided 2026-08-27 — all five took their recommended option. D1 the split symlink key · D2 one hop + marker-gated second · D3 degrade-and-label (+ an on-demand re-probe-with-sudo) · D4 non-listening apps in scope · D5 docker-only DB sizing (standalone deferred to its own spec). Recorded in the 054 concern's Decisions taken; D4 in-scope confirms the partial supersede of 053.

Symlink identity — key on the resolved path, or the logical one? rec: logical for deploy-symlinks, physical otherwise

Keying on the resolved path collapses aliases correctly but makes a current→releases/<ts> deploy fork a brand-new context every release. Keying on the logical path stays stable but won't dedup two links to the same file. The proposed split — dedup on physical, display logical, and promote to logical when the physical matches */releases/* */versions/* — is a real behavioural commitment, not a mechanism. This is the one token with the widest downstream blast radius.

How far the wrapper rule hops — one, or bounded-two? rec: one by default, two only gated on a marker file

A single hop is safe but leaves backend/scripts/run.sh at backend, not the repo root. The bounded double hop reaches the repo root but risks over-grouping independent deployables in a monorepo. The operator's own frontend/backend instruction wants the merge — so the default is chosen, but "monorepos group at their git root" must be documented as intended behaviour.

Privilege posture — require sudo, or degrade gracefully? rec: degrade, and label every degraded number

~80% of the map is unprivileged. The commitment is that a sudo-less deployment returns partial, labelled data — RSS instead of PSS, cgroup instead of per-PID, permission-denied instead of a fake 0, confidence=low on procfs-denied mappings — rather than demanding root. "No PID" must never be silently read as "no process".

Non-listening apps — in scope, or ports-and-docker only? rec: in scope — the ps/systemd/cron sweep is mandatory

If discovery is only ports+docker, every queue worker, cron job, and batch script is invisible. The complementary systemctl list-units --state=running + cron enumeration + ps -eo args interpreter scan is what makes the map complete; those apps emit the same record with an empty port list.

◆Dependencies — what this actually needs installed

  • On the target host: nothing beyond a standard modern Linux — ss/iproute2, coreutils, procps, cgroup v2. The raw-/proc fallbacks need only sh/ls/grep, so even minimal/embedded hosts degrade rather than fail.
  • The Docker CLI already on the host — the only "processor" adopted. Covers Dockerfile-derived metadata (via docker image inspect) and compose canonicalization (via the embedded compose-go) with zero code to maintain.
  • A JSON parser we already have (Jackson) to consume inspect output — pin on the stable inspect fields, no schema library.
  • Explicitly rejected: dockerfile (archived), dockerfile-parse (inactive), embedding compose-go directly (wrong ecosystem, already reachable via the CLI). Building our own Dockerfile parser is unnecessary.
