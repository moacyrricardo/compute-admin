Sequencing · 049 · 050 · 053

What to build first, and the data flow it assumes

049 and 050 are stacked and both red-teamed; 053 proposes an app model that reshapes what 050 emits. This is the order I'd take them in, and the picture of the pipeline that order is protecting.

049 is independent — build it now. Its two blockers are entirely internal and have nothing to do with the app model. Waiting on 053 buys it nothing.

050 is coupled, but by exactly one question. Its core deliverable is the verb mapping, which is the thing 053 redefines. The cost of the wrong order is concrete: editing an approved action resets it to DRAFT, so retrofitting declared verbs means re-approving every lifecycle action already in the field.

Only axis A of 053 gates 050 — where a declaration lives. The other eight open questions (declared-app persistence, MCP tool shape, retiring, 032/033/038 conversion, the hash line) don't block anything.

Fix 053's two false premises before drafting from it, not to unblock work, but because a spec author would otherwise build on option A1's "gate-safe by construction" advantage, which the precedent doesn't actually have.

The pipeline this order protects

The thesis underneath 053 is a single sentence: classification happens once, at discovery, and its output is commands — not a taxonomy the read path re-derives. Everything about the sequencing follows from wanting that shape to survive contact with 049 and 050.

Reading it stage by stage

Stage 1 — evidence. Four detection routes exist today and they are not equal. The port-driven chain (ss -ltnp → PID → /proc) is what 025 built, what 049 extends to folders, and what 050 hangs lifecycle scripts off. But 026 discovers systemd units with no port involvement at all, and 033 states plainly that "No port is required — portless workers and datastores are monitored because they belong to a project." The genuine blind spot is narrower than "portless": it is hand-launched and cron-scheduled native, non-systemd work.

Stage 2 — discovery, and the one thing that matters. Discovery must classify: it is looking at image names, cgroups, cmdlines, marker files. The proposal in 053 is that the output of that classification is a proposed action — a command plus a few declarations — rather than a taxonomy that gets persisted and re-joined later. This is what kills the double-derivation 040 complained about: "what is an app is derived twice."

Stage 3 — the gate, and why order matters. Everything crosses one human approval. Two properties make sequencing consequential rather than cosmetic. First, a CUSTOM action's leading literal path is sha256-pinned at approval and re-probed before every run (015). Second — and this is the reason 050 shouldn't ship on the wrong model — editing an approved action resets it to DRAFT, so retrofitting a declaration onto approved actions means re-approving each one.

Stage 4 — assembly. The browser groups by app-name, splits by part, maps verb to controls, renders by role, and feeds the axes only with readings that declare themselves attributable. Nothing here decides what an app is — that was decided at stage 2 and carried forward.

The red branch is the unresolved one. A declared app arrives at stage 2's output with no evidence behind it — and the 049/050 machinery physically cannot measure it: 049's probe fans out over APP_PORT_LIST with a port as its only param, 050's scan takes PID and appRoot as its only arguments and reads managedBy from the cgroup, and 050's Start "flips the card UP" on port-driven liveness. In v1 a declared app is a thing you can run commands against, not a thing the monitor can measure. That should be stated, not discovered.

The order, and why

  1. Fix 053's two false premises before drafting Not to unblock anything — nothing waits on this. But option A1 is currently sold on "gate-safe by construction — never reaches argv", and 026 binds {app-name} straight into systemctl restart under sudo -n. And Decision 4 is justified by "declared apps are the only route to portless visibility", which two existing discoverers contradict. A spec author would build on both.

  3. 050 drafts against that answer coupled Its own four findings still have to be fixed regardless — the make -C contradiction, the symlink-vs-resolved path, the name-uniqueness rule, the acceptance gaps. 053 fixes none of those.
  4. 049 proceeds in parallel independent Nothing about it waits. Its blockers are the poll tier that 024 doesn't have and the discovery-time run that contradicts its own gate paragraph — both internal.

Why 049 is genuinely independent

049 detects an app's folder and three sizes and feeds the native disk axis. None of that depends on what an app is. Under 053 the only thing that changes is that its proposed footprint action would carry a role declaration alongside the app-name it already carries — and under axis A1 that is a param definition on machinery 026 already uses, so 049's "no new DTO fields, no Flyway migration" constraint survives untouched.

A correction worth recording. An earlier reading of this claimed 049's NDJSON schema "gets rewritten either way" under 053. That does not hold. The NDJSON is the probe's output — a reading. Declarations ride on the proposed action. They are different objects, and under A1 the schema is not touched at all.

Why 050 is the coupled one

050's deliverable is the verb mapping: it renders card controls for actions "named exactly start / stop / restart / deploy", matched client-side. 053 replaces that name-matching with a declaration. Build 050 first and you ship the name-matching, approve actions against it, then have to edit each one — which resets it to DRAFT and demands re-approval.

Two smaller misalignments come with it, both worth deciding at the same time:

  • 053's vocabulary has seven verbs; 050 renders controls for four. status, logs and metrics have no rendering rule.
  • 053 says logs; 026's existing action is named tail-logs. 050's systemd dedup-by-verb has to match them, so a done spec gets touched.
The honest fourth option. Ship 050 on verb-by-name now and accept the migration later. On a single-operator tool that migration is "re-approve a handful of actions" — quite possibly cheaper than blocking on a model decision. This is a real choice, not the wrong one; it just needs to be chosen rather than defaulted into.

The invariants none of this may break
  • Approval is UI-only. Discovery proposes; a human approves; MCP has no approve tool and GateArchTest enforces it.
  • Content-pinning (015) keys on RecipeType.CUSTOM: the leading literal path is hashed at approval and re-probed before every run.
  • S4 — fixed script bodies, typed params, no free-form commands, no operators in an argv.
  • S5 — coverage is bounded by the machine's login user; no new sudo.
  • S9 — host and filesystem topology stays off the MCP surface.

Method

Document analysis only — no source, tests or config were read. The findings this sequencing rests on come from two independent adversarial passes (one classifying the 049/050 red-team against 053, one attacking 053 directly), with the load-bearing facts re-verified by hand against specs/026, specs/033, specs/022 and a repo-wide search for a mis-cited string.
