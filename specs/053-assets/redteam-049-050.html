Redteam · specs 049 & 050

What has to be answered before 049 and 050 can be built

Adversarial read of the two specs as written — document analysis only, no code read. 15 findings, every one anchored to quoted spec text.

Neither spec is ready to hand to an implementer. Both are unusually thorough documents — long Decision sections, explicit resolved-question logs, honest Known Gaps — and the problems are not sloppiness. They are the four or five places where two carefully-made decisions meet and disagree, plus one shared foundation that was never actually decided.

The two that would send a build the wrong way: 049 and 050 disagree about which path a lifecycle action registers (the symlink or the resolved release dir) — and spec-015 hashes that path at approval, so the choice decides whether every redeploy breaks the action or silently runs an old release. And 049's sampling rule refers to a poll tier that spec-024 does not have: 024 offers a single-choice cadence defaulting to single, so under the default the footprint probe may never run at all — and folder + sizes are the whole deliverable.

Underneath both: they are built on spec-040's "thin-BE leaning", and 040 is an open concern that says of itself "this stays a concern, options open." That is not fatal — both specs are compatible with the leaning — but it is an architectural bet neither spec declares as a bet.

Blockers

Four findings that would stall the build or send it in the wrong direction.

blocker

The footprint probe's poll tier does not exist

049 · #1
Lens: buildability gap · undecided-as-decided

049 says the probe runs on “the slowest active tier (1 m / 5 m)”. That phrasing assumes several tiers run at once. Spec-024 defines a single-choice cadence selector — single | 5s | 30s | 1m | 5m — and its default is single. There is no slowest active tier; there is one selection. For three of the five settings, including the default, the spec never says whether footprint runs, runs once, or never runs. Folder and sizes are the entire deliverable of the spec.

Question: with a single-choice cadence, when does the footprint action run under single, 5s and 30s?
Evidence — the two specs side by side
“Sampled, not per-poll (decision). du is IO-heavy, so the footprint probe is not run at the 5 s poll tier. The UI polls it only on the slowest active tier (1 m / 5 m) — and it may run once at discovery for an initial value…” specs/049-todo-app-folder-detection.md · “du gating”
“A cadence selector (single | 5s | 30s | 1m | 5m) stored in the view state; default single. On a non-single cadence, a setInterval re-invokes the same actions…” specs/024-done-monitor-ui-dashboard.md · “Polling”

024 also states it as a product decision: “Client-side poll control (single/5s/30s/1m/5m) with a Run now button”. One control, one value at a time.

blocker

“May run once at discovery” contradicts the gate the same spec defends

049 · #2
Lens: internal contradiction

The sampling decision offers a discovery-time initial run. But this spec's own “Gate untouched” paragraph has the footprint action landing PENDING_APPROVAL and approved by a human in the UI — so at discovery time the action cannot run, and if it could, that is precisely the auto-run of an unapproved action that spec-006's discoverer contract and the spec-004 gate forbid. The word “may” also leaves it as an open choice inside a section labelled a decision.

Question: is the discovery-time initial run dropped outright, or did it mean something else (the first poll after approval)?
Evidence — the contradiction inside one document
“…and it may run once at discovery for an initial value — so folder + sizes lag the fast metrics rather than hammering disk every 5 s.” 049 · “du gating” → Sampled, not per-poll (decision)
“Gate untouched. The footprint action is proposed PENDING_APPROVAL through the unchanged spec-004 gate and approved once, in the UI, like every action — discovery only proposes (spec-006 contract); nothing auto-approves…” 049 · Decision

The same rule is restated in Acceptance: “Run discovery, approve the new footprint action on each app-monitor recipe in the UI… Nothing runs without UI approval.”

blocker

049 and 050 disagree about which path the action registers — and spec-015 hashes it

050 · #8
Lens: cross-spec conflict

049 decides that a symlinked release keeps the symlink as identity because it is stable across redeploys, and explicitly says that is “what spec-050 keys its lifecycle scripts to”. But 050 receives appRoot — which 049 defines as the readlink -f-resolved real directory — as its scan argument, and proposes <root>/start.sh. The two specs cannot both be right about the same argv token.

This is not cosmetic, because spec-015 pins the leading literal: the path is sha256sum'd at approval and re-probed before every run. Register the resolved path and the next redeploy leaves the action pointing at an old release directory (or a path that no longer exists). Register the symlink and the pinned bytes change under it on every deploy, so the next run refuses with a 409 until re-approved — arguably correct, but a very different operator experience.

Question: is the proposed action's leading LITERAL the link path or the resolved appRoot — and if it is the symlink, is re-approval after every deploy the intended workflow?
Evidence — 049's decision, 050's mechanics, 015's consequence
“appRoot is always the readlink -f-resolved real dir; link is what the UI shows as identity (decision: symlink identity is stable across redeploys, the resolved target is secondary).” 049 · NDJSON schema
“…the folder line shows the symlink path as identity (/opt/app/current)… stable across redeploys, which is what spec-050 keys its lifecycle scripts to.” 049 · Implementation sketch → Card
“the app's PID and folder are its only positional arguments (sh -c <SCRIPT> sh <pid> <appRoot>)” 050 · Detection
for f in start.sh run.sh stop.sh kill.sh restart.sh deploy.sh; do
  [ -f "$root/$f" ] && echo "script $root/$f"
done

050 · “By app folder” — $root is $2, the resolved appRoot. The verb table then proposes argv <root>/start.sh.

“ApprovalService.approve sha256sums the leading literal path (ScriptPinService.probe…) and RunService.run re-probes before every run (ScriptModifiedException, 409) — the bytes that run are the bytes a human approved.” 050 · Context, describing spec-015
blocker

The action Shape bullet describes the exact vector the hard constraint bans

050 · #9
Lens: internal contradiction

050's central safety constraint is “register found scripts, never inferred run-commands”, and its not-proposed table rejects Makefiles because running one means synthesizing make -C <root> <target>. Yet the Actions section describes the proposed action shape as a leading literal path plus “optional further LITERALs” and names the make -C <root> start vector as the example. An implementer who reads the Actions section first will build multi-token argvs the rest of the spec forbids three times.

Question: is the multi-LITERAL form dead — or is there a surviving case it was written for?
Evidence — the same example, banned and permitted
“Shape. Each proposed action is a spec-007 CUSTOM-style action: leading LITERAL absolute path, optional further LITERALs (the make -C <root> start vector), sudo = false…” 050 · Actions, the gate & content-pinning
“its argv is that one absolute LITERAL path, run verbatim — no arguments prepended or appended, no shell operators, no loops, no free-form param, ever” 050 · Detection → Verb mapping
“No inferred run-commands. The discoverer must never synthesize a way to run an app from build metadata — no mvnw spring-boot:run, no gradlew bootRun, no npm run start, no make start.” 050 · Hard constraint
“Makefile start/stop/deploy targets — why not proposed: running it means synthesizing make -C <root> <target> — an inferred command…” 050 · Detected but NOT proposed table

Risks

Buildable, but each is a likely-rework or wrong-assumption bet.

risk

Both specs stand on spec-040's leaning — and 040 is an open concern

049 + 050 · #4
Lens: unstated assumption / dependency

Each spec justifies keeping assembly in app.js and adding no backend model by citing “the spec-040 thin-BE leaning”. Spec-040 is todo, it is a concern, and its own heading says the leaning is recorded but the options stay open — with Open Question 1 asking exactly where the BFF line sits, which is the question 049's NDJSON-parsed-in-the-browser design answers by assumption. Both specs are compatible with the leaning, so this is not fatal; the gap is that neither declares it as a bet, and if 040 resolves toward option D (a backend read-model) the client-side assembly in both specs is rework.

Question: is 040's leaning being promoted to a decision before these build — or do 049/050 state the rework risk explicitly and proceed?
Evidence — what 040 says about itself
“Leaning (recorded — this stays a concern, options open) … The stated preference is a really thin backend” specs/040-todo-monitor-runtime-view-and-model-weight.md
“Where exactly is the BFF line? Transient per-request server shaping is allowed; a persisted classification model is not. Is MonitorService's read-time host/app partition + rollup on the allowed side of that line, or should even that move to the client?” 040 · Open Questions #1
“the backend stays ‘run approved script → hand back stdout’ (the spec-040 thin-BE leaning — no persisted classification model, no new table…)” 049 · Decision
“no persisted classification model (spec-040 thin-BE: discovery surfaces commands + params; the UI assembles the controls)” 050 · Decision #4

The catalog agrees it is unresolved: row 040 reads “concern (options open; leaning = thin BE)”.

risk

A slowly-sampled footprint feeds a per-poll disk axis, with no stated behaviour in between

049 · #3
Lens: buildability gap — unspecified behaviour on an obvious path

049 decides two things that meet awkwardly: footprintBytes is deliberately sampled slowly, and footprintBytes feeds the machine's attributed disk axis, which forces a joint edit to spec-041's OTHER computation so the app is not double-counted. But 041 computes other = clamp(host_used − Σ attributed, ≥ 0) on every poll. The spec never says what the axis does between footprint samples — whether the last value is retained, treated as absent, or zero. That choice is the difference between a stable bar, a segment that flickers in and out every poll, and exactly the double-count the spec set out to avoid.

Question: does a stale footprintBytes keep feeding the axis, for how long, and what does the axis show on the first fast poll after a page load?
Evidence — the two decisions and 041's formula
“the footprint probe is not run at the 5 s poll tier… so folder + sizes lag the fast metrics” 049 · du gating
“The native disk % axis is fed from footprintBytes… This is a joint 049 + 041 change: 041's OTHER = host_used − Σ attributed disk computation (computeOther in app.js) must now subtract the newly-attributed native disk bytes as well, or the deployed app double-counts” 049 · Implementation sketch
“Compute other = clamp(host_used − Σ attributed_consumers, ≥ 0) per axis and render” specs/041-done-host-system-usage-segment.md · Decision
risk

049's Acceptance never tests its headline disk-axis decision

049 · #5
Lens: untestable acceptance

Resolved design question 1 makes feeding the disk axis — and amending 041's OTHER math — a headline decision of this spec, and finding #3 above shows it is the subtlest thing in it. The Acceptance section checks the card folder, the three sizes, the build-tree suppression and the unresolved tag. It never mentions the disk axis, the OTHER segment, or double-counting, so the riskiest decision in the spec has no checkable done condition.

risk

Action-name uniqueness is asserted, not established

050 · #10
Lens: buildability gap

050 says losers of a verb contest are proposed under their basename and that “action names are unique within the recipe by construction” — but gives no rule that produces that uniqueness. Take a folder with start.sh and run.sh, launched by an ancestry bash /opt/app/run.sh. start.sh wins start; the folder run.sh loses and becomes run; the ancestry launcher is only mapped to start “if no folder start candidate won”, so it loses too — and the spec never names it. Its natural basename is run, which is taken.

Question: what names a losing ancestry launcher, and what breaks a basename tie?
Evidence — the precedence rule and the ancestry row
“Precedence when several script files map to one verb: the first row wins the verb name; the losers are still proposed under their basename as the action name (run for a losing run.sh) — runnable from the drawer, but not mapped to a card button (name ≠ verb). Action names are unique within the recipe by construction.” 050 · Verb mapping

risk

050's Acceptance skips the three most dangerous behaviours

050 · #12
Lens: untestable acceptance

Acceptance walks a clean path: discovery proposes start/stop, UI approval pins both, an unreadable path 409s, Start runs inline, Stop opens the drawer, editing the script 409s the next run. What it never exercises is everything the spec added for safety: the deploy type-the-app-name gate, the composed restart with its half-failure rule, the proposed:false read-only reporting, and the systemd dedup-by-verb. The composed restart in particular has a stated failure mode — “if start fails after stop succeeds, the app stays down” — with no acceptance check that the guard works.

Question: what is the checkable done condition for composed restart, for the deploy name-typing gate, and for “systemd app ⇒ reported, never proposed”?
Evidence — decisions with no matching acceptance
“Otherwise the UI composes it: run stop, await its terminal run state, then run start… If stop reaches a failed terminal state, start is not auto-run” 050 · Restart composition (decision)
“deploy requires the operator to type the app name to confirm… the Deploy button stays disabled until the typed value equals the card's app name.” 050 · Deploy carries extra friction (decision)
“the scan still reports them in the NDJSON (proposed: false)… but proposes no runnable actions… the UI dedups by verb, preferring the systemd control” 050 · When a systemd-managed app also has folder scripts
“The monitor app card then shows Start and Stop controls: Start runs inline and the card flips UP; Stop opens the confirm/review drawer showing the exact pinned command before running.” 050 · Acceptance — the whole UI assertion

minor

cwd-only or unresolved, offered as an either/or

049 · #7
Lens: undecided-as-decided

The two are distinct values in the schema with different meanings — cwd-only is the honesty label for “heuristics failed, this is just the process cwd”, unresolved is “not even a cwd”. The python section then offers them interchangeably for the same case, and Acceptance expects the python -c straggler to show “unresolved”.

Evidence

minor

The 25 s drain is the wrong knob

050 · #14
Lens: cross-spec inconsistency

050's deploy-safety baseline is stated in terms of a “bounded 25 s window” for draining in-flight runs. In spec-016, 25 s is spring.lifecycle.timeout-per-shutdown-phase; the run drain is ca.run.shutdown-await-seconds, default 20, deliberately kept under the phase timeout. Concern 051 states both numbers correctly, which makes 050 the odd one out.

Evidence
“graceful shutdown (spec-016) drains in-flight runs within a bounded 25 s window on SIGTERM” 050 · Long-running runs
“setAwaitTerminationSeconds(...) — new key ca.run.shutdown-await-seconds (default 20, kept below the 25s phase timeout so the await completes within the …)” specs/016-done-graceful-shutdown-and-run-reconciliation.md
“spec-016's bounded drain (server.shutdown: graceful + timeout-per-shutdown-phase 25s; ca.run.shutdown-await-seconds 20 in AsyncConfig)” specs/051-todo-run-execution-policy.md — states it correctly
minor

Every lifecycle script is assumed not to need privilege

050 · #15
Lens: unstated assumption

sudo = false is set for all proposed actions on the grounds that the folder came from the login user's own process. That follows for reading, but a deploy.sh or restart.sh that touches a system service, a privileged port or a shared data directory routinely needs escalation. The Permissions section bounds discovery coverage honestly; nothing records that a lifecycle script requiring sudo is simply unsupported.

Evidence
“sudo = false (the folder came from the login user's own process; there is nothing to escalate)” 050 · Actions → Shape
“The probe runs as the machine's loginUser, no sudo — so coverage is bounded to apps that user owns” 050 · Permissions & coverage — about the probe, not the proposed action

What held up

verified

050's content-pinning claim is exactly right

050 → 015

050 argues that filing lifecycle actions under RecipeType.CUSTOM buys spec-015 content-pinning “with zero new pinning code”, and that this deliberately flips 015's note that discovered actions are not pinned. Both halves check out against 015 as written — this is the strongest load-bearing argument in the spec, and it is correct.

Evidence — 015's own words
“Discovery (discovery/…). Discoverers propose built-in service recipes (NGINX/DOCKER/DATABASE/CRON), persisted PENDING_APPROVAL… Keying pinning on RecipeType.CUSTOM means discovered actions are not pinned even when a proposed argv leads with an absolute-path LITERAL to a system binary… No discovery change.” specs/015-done-custom-script-content-pinning.md · Impact / blast radius
“This intentionally flips spec-015's ‘discovered actions are not pinned’ note — these discovered actions land under CUSTOM precisely so they are pinned, with zero new pinning code.” 050 · Actions, the gate & content-pinning

Scope & method

Document analysis only — no source file, test or config was opened, which is the point: this judges the specs as written, not an implementation that does not exist yet. Both targets are todo specs, so both are valid; concerns and done specs are out of scope by rule.

Per the brief, implementation detail was left alone — 049's ## Implementation sketch contents and 050's absent ## Implementation section were not judged. Findings #3 and #8 touch mechanics only where a mechanism is the decision (which path gets hashed; what feeds the axis).
